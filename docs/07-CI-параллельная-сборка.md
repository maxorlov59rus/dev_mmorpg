# DevOps: параллельная сборка клиент + сервер

Одно ядро CI/CD управляет двумя независимыми стеками: **клиент UE5.8** (Win64 + Android ARM64)
и **сервер C++ TrinityCore-like** (Linux GCC/Clang, Windows MSVC 2022). Сборки идут
**параллельно на разных агентах**, конвергируются в один релизный бандл.

```
                        ┌─ build:client        (ue58-windows runner, UAT BuildCookRun)
   lint →───────────────┼─ build:server:linux  (ubuntu runner, CMake+Ninja+ccache)
   (fmt/proto/python)   └─ build:server:win    (msvc2022 runner, msbuild+clcache)
                              │        │        │
                              ▼        ▼        ▼
                          test:server-unit / test:proto-golden   (needs: сборки)
                                     │
                                     ▼
                          package:release-bundle                 (needs: ВСЕ успех)
                                     │
                            deploy:dev-shard → deploy:staging    (manual)
```

## Файлы

| Путь | Назначение |
|---|---|
| `build/build_config.json` | Единая конфигурация: пути к UE, ветки, цели, флаги UAT/CMake, таймауты. Читается оркестратором и локальными разработчиками. |
| `build/BuildOrchestrator.py` | Python-оркестратор (asyncio): спин-ап 3 задач одновременно, `gather`, **Fail Fast** (отмена оставшихся + вывод хвостов логов всех задач), этап Packaging с `release_manifest.json` и sha256. |
| `.gitlab-ci.yml` | Пайплайн GitLab CI: stages `lint → build → test → package → deploy`, параллельные джобы сборки, `needs:` для конвергенции, кешируемые компиляции. `lint:cpp-format` детерминирован: стиль задаётся корневым `.clang-format` (LLVM + IndentWidth 4, ColumnLimit 100), команда вызывается **без** `--style`, версия clang-format зафиксирована переменной `CLANG_FORMAT_VERSION`. Локально: `find dm-server Plugins Source -name '*.h' -o -name '*.cpp' | xargs clang-format -i`. |
| `build/scripts/BuildClient.bat` | UAT Wrapper: парсинг `--platforms=` / `--config=`, очистка Intermediate/Saved/Binaries, отдельный проход компиляции C++ (UBT), cook только запрошенных платформ, `-iterate` режим. |
| `build/ServerBuild.sh` | CMake wrapper (Linux): проверка зависимостей (Boost/OpenSSL/MySQL/Lua/Ninja) **до** configure, ccache launcher, configure→build→ctest(smoke)→install. |
| `build/scripts/ServerBuild.bat` | Тот же контракт для Windows: vcpkg toolchain, clcache через `CMAKE_VS_GLOBALS`, VS 2022 generator. |

## Локальный запуск

```bash
# Показать команды без запуска (проверка конфига):
python3 build/BuildOrchestrator.py --dry-run --targets all

# Параллельная сборка всего + упаковка:
python3 build/BuildOrchestrator.py --config build/build_config.json --targets all

# Только сервер Linux, чистая пересборка, без упаковки:
python3 build/BuildOrchestrator.py --targets server_linux --clean --skip-package

# Не отменять соседние задачи при падении одной (собрать все логи):
python3 build/BuildOrchestrator.py --targets all --no-fail-fast
```

Коды возврата: `0` успех, `1` сборка упала (fail-fast или no-fail-fast),
`2` ошибка конфигурации, `124` timeout задачи, `127` бинарь агента недоступен.

## Ключевые решения

1. **Fail Fast реализован через `asyncio.wait(FIRST_EXCEPTION)`**, а не «наивный»
   `gather`: при падении первой задачи остальные корутины **отменяются**, дочерние
   процессы убиваются (`taskkill /T` на Win / `proc.kill()` на Linux) — иначе
   90-минутный cook клиента продолжит жрать агент после упавшей 3-минутной сборки сервера.
   После отмены обязательно дожидаемся `proc.wait()` под `shield`, чтобы не ловить
   `RuntimeError: Event loop is closed` на закрытии event loop.
2. **Логи каждой задачи пишутся в собственный файл** `build/logs/<task>_<ts>.log`
   и стримятся в консоль с префиксом `[task|сек]`; при падении печатаются хвосты
   **всех** задач — диагностика без захода на агентов.
3. **Конвергенция в CI**: `package` имеет `needs:` на client **и** оба серверных джоба —
   бандл физически не может собраться из частично успешного пайплайна.
4. **Кеширование**: ccache (Linux, `CCACHE_BASEDIR` + content-check компилятора) и
   clcache (Windows, проброс через `CMAKE_VS_GLOBALS`) между пайплайнами через
   gitlab-кеш по `${CI_COMMIT_REF_SLUG}`.
5. **Изменения протокола ломают pipeline рано**: `lint:proto-drift` сверяет
   `proto/opcodes.defs` со сгенерированными заголовками (единый источник истины).
6. **UE-специфика Android**: cook/пакет идёт с `-architectures=...;Android:arm64`,
   ASTC-конфиг `Development_ASTC`; NDK требуется только клиентскому раннеру
   (`ue58-windows`), серверным агентам он не ставится.
